## 1. Obiettivo e scope

Permettere all'amministratore di definire, **per ciascuna origine di addebito e per
ciascuna scadenza**, la percentuale di quell'origine che cade in quella rata. Le due
"filosofie" che girano tra gli amministratori non sono due funzionalità: sono due
input dello stesso meccanismo.

- *Front-load del pregresso* → `saldo_iniziale` = `[r1: 100%, r2: 0%, r3: 0%]`,
  `preventivo` = `[r1: 50%, r2: 25%, r3: 25%]`
- *Spalmatura* → `saldo_iniziale` = `[r1: 50%, r2: 50%]`, `preventivo` = `[r1: 50%, r2: 50%]`

Il software non arbitra quale sia "corretta": resta fedele a ciò che l'assemblea ha
deliberato. Conseguenza diretta sul modello dati: **la Rata smette di essere un
importo monolitico e diventa un contenitore** di allocazioni per origine.

### In scope (v1.10)
- Enum `OrigineQuota` e mappatura sorgenti.
- Tabella di configurazione (intento a percentuali) + tabella celle (verità in cent).
- Generatore con quadratura al centesimo bidimensionale.
- `saldo_iniziale` come voce dinamica incassabile nei tre modi (Rata 0 / accorpata r1 / frazionata).
- Validazioni, invarianti, suite Pest.
- Migrazione retrocompatibile dei piani esistenti.

### Fuori scope — deferred
- **`conguaglio` (differenza preventivo/consuntivo per condòmino)**: l'origine è
  prevista nell'enum ma resta *reserved* finché non esiste il consuntivo che la
  produce → modulo di chiusura esercizio (Year End Master). Quando arriva, è "solo
  un'altra origine": zero nuova infrastruttura.
- **Day-split dei subentri** (pro-rata temporis del preventivo + regole di esigibilità
  del pregresso) → v1.11 (Recupero Crediti). Questo spec *predispone il substrato*
  (celle esatte e taggate per origine), non implementa lo split.
- **Link granulare voce ↔ quota** (`riga_fattura_id` / `voce_id`) → v1.11. L'origine
  è uno strato più grossolano e compatibile.

## 2. Principio architetturale

Stessa primitiva del motore di riparto unificato: pesi su un asse. Qui i pesi cadono
sulle **scadenze** invece che sulle unità immobiliari. L'amministratore versa nella
primitiva la distribuzione deliberata; il generatore produce celle esatte al
centesimo; tutto il resto sono proiezioni sul giornale.

Distinzione che regge l'intero impianto contabile:

| Tipo di origine | Esempio | Genera scrittura di emissione? | Ruolo dell'allocazione sulle rate |
|---|---|---|---|
| **Contabilizzante** | `preventivo`, `straordinario`, `fondo` | **Sì** | L'allocazione *è* parte dell'emissione: scandisce quanto credito matura e quando |
| **Di sola pianificazione** | `saldo_iniziale`, `conguaglio` | **No** | Il credito **esiste già** (scrittura di apertura / chiusura esercizio). L'allocazione assegna solo scadenze e governa l'imputazione degli incassi su un credito preesistente |

Questo è il punto che evita il bug peggiore: **il saldo iniziale non si ri-emette.**
Lo stabilisce la scrittura di apertura (oggi la Rata Zero sintetica da migrazione);
spalmarlo su `r1..rn` è *scheduling*, non una nuova scrittura. Stornarne la
pianificazione = ri-schedulare, non invertire il giornale (il credito resta).

## 3. Enum `OrigineQuota`

PHP Backed Enum, persistito `VARCHAR(50)` (convenzione progetto).

```php
enum OrigineQuota: string
{
    case Preventivo    = 'preventivo';     // contabilizzante — gestione ordinaria corrente
    case Straordinario = 'straordinario';  // contabilizzante — art. 1135, lavori/ad personam
    case Fondo         = 'fondo';          // contabilizzante — accantonamento (Voci Accantonamento v1.10)
    case SaldoIniziale = 'saldo_iniziale'; // pianificazione — apertura / Rata Zero
    case Conguaglio    = 'conguaglio';     // pianificazione — RESERVED, attivo da Year End Master

    /** L'origine produce una scrittura di emissione, o è schedulazione su credito preesistente? */
    public function generaScritturaEmissione(): bool
    {
        return match ($this) {
            self::Preventivo, self::Straordinario, self::Fondo => true,
            self::SaldoIniziale, self::Conguaglio              => false,
        };
    }

    /** Esposta in UI in v1.10? (conguaglio nascosta finché non c'è il consuntivo) */
    public function disponibileV110(): bool
    {
        return $this !== self::Conguaglio;
    }
}
```

### Mappatura sorgenti del totale per origine
- `preventivo` → Σ degli importi dei `piano_rate_capitoli` (snapshot delle foglie deliberate). `[VERIFICA]`
- `straordinario` → importi del piano straordinario / addebiti ad personam.
- `fondo` → voci di accantonamento (dipendenza: Voci Accantonamento v1.10).
- `saldo_iniziale` → scrittura di apertura / `CanonicalTitolarità.saldo_iniziale`. `[VERIFICA]`
- `conguaglio` → output del modulo di chiusura esercizio (futuro).

> Nota di riconciliazione: `OrigineQuota` è **ortogonale** al `tipo_piano`
> esistente (ordinario/straordinario, che porta semantica di autorizzazione ex
> art. 1135). Un piano ordinario può ora mescolare `preventivo` + `saldo_iniziale`
> sulle stesse rate. Confermare in sezione 11 se `straordinario` resta piano a sé o
> diventa anch'esso un'origine all'interno di un piano misto.

## 4. Modello dati

Tre interventi additivi: un enum (sopra), due tabelle, una colonna. Niente che cambi
la cardinalità di `rate_quote`.

### 4.1 `piano_origine_scadenza` — configurazione (l'intento a percentuali)

```php
Schema::create('piano_origine_scadenza', function (Blueprint $table) {
    $table->id();
    $table->foreignId('piano_rate_id')->constrained()->cascadeOnDelete();
    $table->string('origine', 50);                 // OrigineQuota
    $table->unsignedTinyInteger('rata_numero');    // 0 ammesso (Rata Zero)
    $table->unsignedSmallInteger('percentuale_bp');// basis points 0..10000 (33,33% = 3333) — INTENTO
    $table->timestamps();

    $table->unique(['piano_rate_id', 'origine', 'rata_numero']);
});
```

`percentuale_bp` è **advisory**: non determina mai un importo memorizzato (vedi §5).

### 4.2 `rate_quota_origine` — celle (la verità in cent)

La cella atomica `(immobile × rata × origine)`. È ciò che rende `rate_quote` un
contenitore e ciò che abilita i subentri.

```php
Schema::create('rate_quota_origine', function (Blueprint $table) {
    $table->id();
    $table->foreignId('rate_quota_id')->constrained('rate_quote')->cascadeOnDelete();
    $table->string('origine', 50);                 // OrigineQuota
    $table->bigInteger('importo_cents');           // verità — può essere 0 (rata a 0% per quell'origine)
    $table->timestamps();

    $table->unique(['rate_quota_id', 'origine']);
});
```

Invariante di composizione: `rate_quote.importo_cents == Σ rate_quota_origine.importo_cents`
per quel `rate_quote_id`. `is_contabilizzante` **non** si memorizza: è derivabile via
`OrigineQuota::generaScritturaEmissione()`.

`[VERIFICA]` Assunzione: `rate_quote` è alla grana `(rata × immobile)` e porta già
`immobile_id` (propagato da `RataQuote` da `StoreIncassoRateAction`). Le celle
ereditano `immobile_id` via la FK. Per le quote condominiali `immobile_id` deve essere
valorizzato — coerente con il check constraint pianificato `chk_immobile_condominiale`.

### 4.3 Colonna su `piano_rate`

```php
$table->string('metodo_arrotondamento', 50)->default('ultima_non_nulla');
// 'ultima_non_nulla' (default) | 'prima_non_nulla'  — uno per piano (vedi §5.2)
// 'resto_massimo' (Hamilton): non esposto in UI v1.10 — vedi nota §5.2
```

> Non si introduce alcuna tabella di "snapshot totali per origine": i totali sono
> ricostruibili dalle celle (`Σ celle per origine = totale origine`). Le celle **sono**
> lo snapshot del risultato, coerentemente con come `piano_rate_capitoli` snapshotta le
> foglie. Se i totali cambiano *prima* dell'emissione, si rigenera; *dopo* l'emissione,
> sono congelati e le correzioni passano da storno.

## 5. Quadratura al centesimo — il cuore

> Risposta diretta alla domanda "come gestisci la quadratura se si permettono
> percentuali arbitrarie": **la percentuale non genera mai l'importo memorizzato.**
> Genera un *target*; una rata-compensatore assorbe il resto e chiude all'esatto totale
> in cent. Per costruzione non esiste scenario in cui i centesimi sfuggono.

### 5.1 Il problema è bidimensionale

Due arrotondamenti, non uno:
- **Orizzontale** — riparto del totale per origine tra gli immobili (millesimi).
- **Verticale** — split della quota per origine tra le rate (percentuali).

Non puoi avere *simultaneamente*, con cent interi e nel caso generale: (a) totale per
rata aggregato esattamente uguale a `percentuale × totale`, (b) totale per immobile
esatto su tutte le rate, (c) riparto esatto. **Devi scegliere quale dimensione possiede
la verità.** Per un sistema ledger-centrico con subentri, l'unità fatturabile atomica è
la **quota del singolo immobile**: quindi è l'immobile a possedere la verità, e il
totale aggregato di rata è una somma derivata.

### 5.2 Regola di compensazione (1D, per ogni vettore)

Dato un totale `T` (cent) e un vettore di percentuali `p_i` (bp):

**`ultima_non_nulla` (default — standard bancario e contabile):**
```
per i in [tutte le rate con p_i > 0 tranne l'ultima]:
    r_i = intdiv(T × p_i, 10000)        // troncamento intero puro, zero aritmetica float
rata_compensatore = ULTIMA rata con p_i > 0   (non l'ultima in assoluto!)
r_compensatore = T − Σ(r_i già assegnati)     // sempre ≥ 0 per costruzione
```
`intdiv` garantisce `r_i ≤ T × p_i / 10000`, quindi `Σ r_i ≤ T` e la compensatrice è
sempre `≥ 0` — impossibile andare in negativo. Con `round`, se più rate arrotondano per
eccesso la compensatrice può diventare negativa (bug silenzioso). Ecco perché il
troncamento è lo standard nei sistemi bancari. Massimo drift sulla compensatrice:
`≤ (n−1)` cent — qualche centesimo nei casi reali. La compensatrice è l'ultima rata
*non nulla*: con `saldo_iniziale = [100%, 0%, 0%]` la compensatrice è r1, non r3.

**`prima_non_nulla` (spazzata iniziale — preferita da alcuni amministratori):**
```
rata_compensatore = PRIMA rata con p_i > 0
per i in [tutte le altre rate con p_i > 0]:
    r_i = intdiv(T × p_i, 10000)
r_compensatore = T − Σ(r_i già assegnati)
```
Carica il drift sulla prima rata; le rate successive con la stessa percentuale
risultano identiche e "pulite". Logica speculare a `ultima_non_nulla`: stessa robustezza,
stessa semplicità di spiegazione in assemblea ("i centesimi di arrotondamento stanno
sempre nella prima/ultima rata").

> **Nota su Hamilton / `resto_massimo`**: metodo eccellente per i sistemi elettorali
> (riparto dei seggi), sconsigliato in contabilità perché distribuisce il drift
> *dinamicamente* in base ai resti frazionari — impossibile spiegare a un condòmino
> perché ha un centesimo in più su r2 rispetto al vicino senza tirare fuori la teoria
> dei resti. In contabilità la **prevedibilità** vince sull'eleganza matematica. Non
> esposto in UI v1.10; disponibile come costante interna se mai servisse in futuro.

Entrambi i metodi esposti sono **esatti** (`Σ r_i = T`). La scelta è di preferenza
amministrativa, configurabile per piano.

### 5.3 Algoritmo del generatore (2D, per-immobile-first)

```
per ogni origine o del piano:
    T_o = totale per origine (da §3.1)

    # --- ORIZZONTALE: split esatto per immobile (millesimi/riparto) ---
    per ogni immobile m:
        quota[m,o] = intdiv(T_o * peso[m], Σ pesi)
    compensa l'immobile-compensatore (ultimo) così che
        Σ_m quota[m,o] == T_o          # INV-2 esatto

    # --- VERTICALE: split della quota di ciascun immobile tra le rate ---
    per ogni immobile m:
        applica la regola §5.2 a (quota[m,o], vettore percentuali di o)
        → cella[m,o,r] per ogni rata r
        Σ_r cella[m,o,r] == quota[m,o]  # INV-1 esatto, per ogni (m,o)

persisti le celle in rate_quota_origine
aggiorna rate_quote.importo_cents = Σ_o cella[m,o,r]   # INV-3
```

Ogni quota d'immobile è auto-contenuta ed esatta → quando in v1.11 un immobile cambia
proprietario a metà anno, lo split è pulito: nessuna contaminazione tra immobili.

### 5.4 Esempio numerico

`preventivo` `T = 100,00 € = 10000 cent`; 3 immobili, millesimi `[333, 334, 333]`;
percentuali `r1 50%, r2 25%, r3 25%`; metodo `ultima_non_nulla`.

Orizzontale: A=3330, B=3340, C=3330 (Σ=10000 ✓).

Verticale (compensatrice = r3, con `intdiv`):

| Immobile | r1 (50%) | r2 (25%) | r3 (resto) | Σ riga |
|---|---|---|---|---|
| A (3330) | 1665 | 832 | **833** | 3330 ✓ |
| B (3340) | 1670 | 835 | **835** | 3340 ✓ |
| C (3330) | 1665 | 832 | **833** | 3330 ✓ |
| **Σ rata** | **5000** | **2499** | **2501** | **10000 ✓** |

A: `intdiv(3330×5000,10000)=1665`; `intdiv(3330×2500,10000)=floor(832,5)=832`; r3=3330−1665−832=**833**.
B: `intdiv(3340×5000,10000)=1670`; `intdiv(3340×2500,10000)=835`; r3=835. C: identica ad A.

Da notare: aggregato r2 = 2499 (target 2500), r3 = 2501 (target 2500): **drift di 1 cent a
livello aggregato**, perché ogni immobile tronca per sé. Per-immobile, per-origine e totale
generale restano **esatti**. È il trade-off di §5.1 reso concreto, ed è quello giusto:
ciò che si fattura e ciò che entra a giornale sono le quote per immobile, non
l'aggregato (che è una proiezione).

### 5.5 Il caso 33,33% × 3

Se l'amministratore inserisce `[33,33%, 33,33%, 33,33%]` = `[3333, 3333, 3333]` bp, la
somma è 9999 bp (99,99%), **non** 10000. Non importa: la percentuale è advisory.
`T = 10000` → r1 = `intdiv(10000×3333, 10000)` = 3333, r2 = 3333, **r3 (compensatrice)** =
10000 − 3333 − 3333 = **3334**. Esatto, e l'amministratore non ha dovuto inserire
33,34 da nessuna parte. Con `round` il risultato sarebbe identico qui (nessuna parte
frazionaria), ma su totali non tondi `round` può spingere la compensatrice sotto zero
— `intdiv` non può.

La validazione (§9) **tollera** scostamenti sub-percentuali della somma in bp
(arrotondamento legittimo) e **avvisa** solo oltre una soglia grossolana (probabile
refuso, es. > 0,5%).

### 5.6 Relazione con il codice esistente — due helper coesistenti

`GenerateRateQuotesAction` (v1.9.x) contiene già `$calcolaFettina`, helper per la
divisione **uguale** in N parti:

```php
// Esistente — divisione uniforme, resto distribuito sulle PRIME rate
$calcolaFettina = function($totale, $numRate, $rataAttuale) {
    $base  = intdiv($totale, $numRate);
    $resto = $totale % $numRate;
    $segno = $totale < 0 ? -1 : 1;
    return ($rataAttuale <= abs($resto)) ? $base + $segno : $base;
};
```

Questo helper **non va modificato**: serve i modi 1–3 (§6) e rimane l'implementazione
canonica per la distribuzione uniforme. Distribuisce il resto sui primi N "slot" — logica
speculare alla `prima_non_nulla` dello spec, ma integrata in un'unica funzione.

Per le percentuali libere (modo 4) si aggiunge `$calcolaFettinaPercentuale` separata:

```php
// Nuovo v1.10 — vettore percentuali libere, compensatrice = ultima non nulla
$calcolaFettinaPercentuale = function(int $totale, array $bpPerRata): array {
    // $bpPerRata = [rata_numero => percentuale_bp]
    $nonNulle       = array_filter($bpPerRata, fn($bp) => $bp > 0);
    $ultimaNonNulla = array_key_last($nonNulle);
    $risultati      = [];
    $sommaParziale  = 0;

    foreach ($nonNulle as $rataNum => $bp) {
        if ($rataNum === $ultimaNonNulla) {
            $risultati[$rataNum] = $totale - $sommaParziale; // compensatrice — sempre ≥ 0
        } else {
            $quota             = intdiv($totale * $bp, 10000);
            $risultati[$rataNum] = $quota;
            $sommaParziale    += $quota;
        }
    }
    return $risultati;
};
```

Le rate con `bp = 0` non compaiono nel risultato; le celle corrispondenti avranno
`importo_cents = 0` (ammesso, vedi INV-1). I due helper sono **ortogonali**: nessuna
modifica al codice esistente, solo un branch sul `metodo_distribuzione` nell'action.

## 6. Saldo Iniziale come voce dinamica — i quattro modi

I modi richiesti **non sono rami di codice**: sono vettori di percentuali per l'origine
`saldo_iniziale`. La Rata 0 non è un caso speciale, è "saldo allocato interamente a una
rata numerata 0".

**Mappatura al `metodo_distribuzione` esistente su `piani_rate`** (campo già presente
in produzione, confermato da `GenerateRateQuotesAction`):

| Modo | `metodo_distribuzione` | Vettore `saldo_iniziale` | Vettore `preventivo` | Helper |
|---|---|---|---|---|
| **1 — Rata 0 autonoma** *(default corrente)* | `'rata_zero'` | `r0: 100%` | `r1..rN` | `$calcolaFettina` |
| **2 — Accorpata in r1** | `'prima_rata'` | `r1: 100%` | `r1..rN` | `$calcolaFettina` |
| **3 — Frazionata uguale** | `'tutte_rate'` | `r1..rN: (1/N) each` | `r1..rN: (1/N) each` | `$calcolaFettina` |
| **4 — Frazionata custom** *(nuovo v1.10)* | `'percentuale_custom'` | vettore libero | vettore libero | `$calcolaFettinaPercentuale` |

I modi 1–3 usano già `$calcolaFettina` (divisione uguale) e restano invariati. Il modo 4
aggiunge il valore `'percentuale_custom'` al campo esistente e instrada su
`$calcolaFettinaPercentuale` (vedi §5.6). La retrocompatibilità è garantita: nessun piano
esistente tocca il modo 4 a meno che l'amministratore lo selezioni esplicitamente.

Poiché `saldo_iniziale` è di sola pianificazione (§2), in tutti e quattro i modi **non si
genera scrittura di emissione**: il credito è quello della scrittura di apertura; le celle
assegnano solo le scadenze e governano l'imputazione degli incassi.

**Nota su D4 (Rata Zero e conflazione):** la revisione del codice chiarisce che la FASE 0
di `GenerateRateQuotesAction` crea la Rata Zero come rata separata con `tipo='saldo_iniziale'`
e `importi.quota_pura_gestione=0`, mentre le FASE 1 (rate ordinarie) gestisce i saldi con
`importi.saldo_usato`. La separazione credito/schedulazione esiste già implicitamente — il
refactor v1.10 la formalizza nelle celle `rate_quota_origine` senza cambiare il
comportamento esterno. D4 si considera **parzialmente risolta**: il codice non conflaziona,
ma la rappresentazione formale nel ledger va ancora verificata (vedi §7).

## 7. Impatto sul giornale e immutabilità

- **Origini contabilizzanti** (`preventivo`/`straordinario`/`fondo`): l'emissione delle
  rate produce la scrittura di emissione `[VERIFICA] DARE Crediti v/Condòmino / AVERE
  <controparte di competenza>`. Per il fondo vale già la logica vista: emissione
  `DARE Crediti / AVERE Fondo`. La composizione dell'AVERE di una rata mista dipende
  dalle origini contabilizzanti che contiene.
- **Origini di sola pianificazione** (`saldo_iniziale`/`conguaglio`): **nessuna
  scrittura all'allocazione.** L'incasso imputato alla rata riduce il credito
  preesistente.
- **Imputazione incasso → origine**: serve sapere *quanto* di un incasso va su
  preventivo vs saldo. Raccomandazione (D3): **unico mastro di controllo "Crediti
  v/Condòmini" con `origine` come dimensione analitica** sulla `riga_scrittura`
  (estendendo la propagazione di `immobile_id` già in essere). "Quanto del saldo
  iniziale è stato incassato" diventa una proiezione sul giornale filtrata per origine —
  coerente con l'impostazione ledger-centrica e a basso impatto sul piano dei conti.
  Alternativa: sotto-mastri distinti per origine. Da confermare contro il piano dei
  conti reale e contro come è imputata la Rata Zero.
- **Immutabilità**: prima dell'emissione le celle sono liberamente rigenerabili; dopo
  l'emissione sono congelate e le correzioni passano da storno (storno-sotto-il-cofano
  sotto soglia, hard-lock alle soglie banca/AdE/assemblea). Il credito sottostante al
  `saldo_iniziale` può già essere oltre una soglia hard (se importato/riconciliato): la
  ri-schedulazione **non lo tocca**, agisce solo sul calendario.

## 8. Predisposizione subentri (consumato in v1.11)

Il vaso di Pandora è reale, ma v1.10 non lo apre: lo **predispone**. Ciò che questo
spec garantisce e che v1.11 consuma:

1. **Celle esatte e taggate per origine** a grana `(immobile × rata × origine)`.
2. **Auto-contenimento per immobile** (§5.3): la quota di un immobile è esatta sulle
   sue rate, indipendente dagli altri.

In v1.11 il motore di recupero/subentri legge queste celle e applica regole diverse per
origine — ed è *per questo* che l'isolamento per origine è obbligatorio, non estetico:

- Celle `preventivo` su rate che cadono nel periodo di possesso del nuovo proprietario →
  **pro-rata temporis** sui giorni esatti di possesso.
- Celle `saldo_iniziale` / `conguaglio` → seguono regole di **esigibilità** e
  tipicamente accordi privati nel rogito; di norma **non** si frazionano per giorni e
  restano in capo al venditore.

Senza il tag d'origine sulla cella, un conguaglio spalmato su rate successive a un
subentro sarebbe indistinguibile dal preventivo corrente, e l'attribuzione diventerebbe
impossibile — esattamente il rischio che hai segnalato.

## 9. Validazioni e invarianti

Invarianti (asserzioni testabili):

- **INV-1** (verticale, per `(immobile, origine)`): `Σ_rate cella = quota[immobile,origine]`. Esatto.
- **INV-2** (orizzontale, per origine): `Σ_immobili quota = totale_origine`. Esatto.
- **INV-3** (composizione): `rate_quote.importo_cents = Σ_origine cella`. Esatto.
- **INV-4** (totale): `Σ tutte le celle = Σ totali per origine`. Discende da INV-1+INV-2.
- **INV-5** (advisory): nessun importo memorizzato è prodotto direttamente da una
  percentuale; sempre via target + compensatrice.
- **INV-6** (`immobile_id` obbligatorio sulle quote condominiali): allineato a
  `chk_immobile_condominiale`.
- **INV-7** (no doppia emissione): le origini di sola pianificazione non rigenerano
  scritture di emissione.

Validazioni di input:
- Per ogni origine, `Σ percentuali_bp` ≈ 10000 entro tolleranza (default ±50 bp =
  ±0,5%). Sotto soglia → accetta (la compensatrice chiude in cent). Sopra soglia →
  blocca con messaggio (probabile refuso).
- Almeno una rata con `percentuale_bp > 0` per ogni origine presente.
- `percentuale_bp` in `[0, 10000]`.
- Modifica delle percentuali/celle vietata se le rate sono già emesse (→ percorso storno).

## 10. Migrazione e retrocompatibilità

Strettamente additiva. I piani esistenti continuano a funzionare leggendo
`rate_quote.importo_cents` (invariato).

### Contesto: cosa esiste già in produzione

La revisione di `GenerateRateQuotesAction` ha rivelato che l'infrastruttura portante
è già presente — la migrazione è più semplice del previsto:

- **`rate_quote.regole_calcolo`** (JSON): ogni quota conserva già la decomposizione
  `importi.quota_pura_gestione` (preventivo) + `importi.saldo_usato` (saldo iniziale).
  È la **fonte di migrazione diretta** per `rate_quota_origine` — nessuna ricostruzione.
- **`piani_rate.metodo_distribuzione`**: campo già esistente con valori `'rata_zero'`,
  `'prima_rata'`, `'tutte_rate'`. La v1.10 aggiunge solo `'percentuale_custom'`.
- **`regole_calcolo.dettagli_saldo`** / **`meta_storico`**: provenienza storica del
  saldo per ogni quota — va preservato (vedi D10).

### Backfill (data migration)

**Step 1 — Celle `rate_quota_origine` da `regole_calcolo`**

```php
RataQuote::whereNotNull('regole_calcolo')
    ->cursor()
    ->each(function (RataQuote $rq) {
        $snap    = json_decode($rq->regole_calcolo, true);
        $importi = $snap['importi'] ?? null;
        if (!$importi) return;

        $celle = [];

        if (($importi['quota_pura_gestione'] ?? 0) != 0) {
            $celle[] = [
                'rate_quota_id' => $rq->id,
                'origine'       => 'preventivo',
                'importo_cents' => $importi['quota_pura_gestione'],
            ];
        }
        if (($importi['saldo_usato'] ?? 0) != 0) {
            $celle[] = [
                'rate_quota_id' => $rq->id,
                'origine'       => 'saldo_iniziale',
                'importo_cents' => $importi['saldo_usato'],
            ];
        }

        // Fallback: quote pre-v1.9 senza decomposizione in regole_calcolo
        if (empty($celle)) {
            $celle[] = [
                'rate_quota_id' => $rq->id,
                'origine'       => 'preventivo',
                'importo_cents' => $rq->importo,
            ];
        }

        RataQuotaOrigine::insert($celle);
    });
```

Le Rata Zero (`numero_rata = 0`, `tipo = 'saldo_iniziale'`) hanno già
`quota_pura_gestione = 0` e `saldo_usato = importo_totale` — nascono direttamente
dallo Step 1 senza logica aggiuntiva.

**Step 2 — `piano_origine_scadenza` dai piani esistenti**

I piani esistenti usano divisione uniforme: ricostruire il vettore percentuali dal
`metodo_distribuzione` e dal numero di rate ordinarie del piano.

```php
PianoRate::cursor()->each(function (PianoRate $piano) {
    $nRate = $piano->rate()->where('numero_rata', '>', 0)->count();

    match ($piano->metodo_distribuzione) {

        'rata_zero' => [
            // saldo_iniziale tutto su r0
            inserisciOrigineScadenza($piano->id, 'saldo_iniziale', 0, 10000),
            distribuisciUniforme($piano->id, 'preventivo', $nRate),
        ],

        'prima_rata' => [
            // saldo_iniziale tutto su r1, preventivo uniforme
            inserisciOrigineScadenza($piano->id, 'saldo_iniziale', 1, 10000),
            distribuisciUniforme($piano->id, 'preventivo', $nRate),
        ],

        'tutte_rate' => [
            // entrambe le origini uniformi su r1..rN
            distribuisciUniforme($piano->id, 'saldo_iniziale', $nRate),
            distribuisciUniforme($piano->id, 'preventivo', $nRate),
        ],

        default => distribuisciUniforme($piano->id, 'preventivo', $nRate),
    };

    $piano->update(['metodo_arrotondamento' => 'ultima_non_nulla']);
});

// Helper: N righe con bp uniforme + compensatrice sull'ultima
function distribuisciUniforme(int $pianoId, string $origine, int $nRate): void {
    $base  = intdiv(10000, $nRate);
    $resto = 10000 % $nRate;
    for ($r = 1; $r <= $nRate; $r++) {
        $bp = ($r === $nRate) ? $base + $resto : $base;
        DB::table('piano_origine_scadenza')->insert([
            'piano_rate_id'   => $pianoId,
            'origine'         => $origine,
            'rata_numero'     => $r,
            'percentuale_bp'  => $bp,
        ]);
    }
}
```

**Step 3 — Verifica post-backfill (obbligatoria, non a campione)**

```php
// INV-3: rate_quote.importo deve coincidere esattamente con Σ celle
$violazioni = DB::select("

    HAVING rq.importo != COALESCE(SUM(rqo.importo_cents), 0)
");

```

## 11. Decisioni aperte

- **D1 — Tabella celle vs flatten.** Raccomandato per v1.10: tabella figlia
  `rate_quota_origine` (additiva, non cambia la cardinalità di `rate_quote`). Opzione:
  appiattire `origine` dentro `rate_quote` (più righe per `rata × immobile`) durante
  l'unificazione del motore di riparto in v1.11.
- **D2 — Riconciliazione con `tipo_piano`.** `straordinario` resta piano a sé (semantica
  autorizzativa art. 1135) o diventa un'origine in un piano misto? Da confermare contro
  il modello attuale dei piani.
- **D3 — Mappatura a giornale.** Mastro unico "Crediti v/Condòmini" + `origine` come
  dimensione analitica (raccomandato) vs sotto-mastri distinti per origine. Dipende dal
  piano dei conti e da come è imputata oggi la Rata Zero.
- **D4 — Refactor Rata Zero.** *(Parzialmente risolta)* Il codice non conflaziona: FASE 0
  crea la Rata Zero con `saldo_usato = importo`, FASE 1 gestisce i saldi nelle rate ordinarie.
  Rimane da verificare la rappresentazione formale nel ledger (§7).
- **D5 — Metodo di arrotondamento di default.** `ultima_non_nulla` (raccomandato: standard
  bancario; la compensatrice è in coda, meno visibile) vs `prima_non_nulla` (preferita
  da alcuni amministratori: rate successive "pulite"). Entrambi con `intdiv`. Configurabile
  a livello piano. `resto_massimo` (Hamilton) non esposto in UI v1.10.
- **D6 — Stub `conguaglio`.** Inserire il valore enum ora come *reserved* (nessuna UI)
  così che Year End Master si innesti senza migrazione. Raccomandato: sì.
- **D7 — Soglia di tolleranza percentuale** per il warning di validazione (proposta ±0,5%).
- **D8 — Estensione `metodo_distribuzione`.** Il campo esiste già con valori
  `'rata_zero'`/`'prima_rata'`/`'tutte_rate'`. Per la distribuzione custom due opzioni:
  (a) aggiungere il valore `'percentuale_custom'` e continuare a usarlo come discriminante
  rapido (raccomandato v1.10 — retrocompatibile, zero rischio); (b) deprecare il campo e
  derivare sempre il metodo da `piano_origine_scadenza` come fonte unica di verità.
  L'opzione (b) è architetturalmente più pulita ma richiede due step (backfill → deprecazione);
  candidata per v1.11 con unificazione motore.
- **D9 — Collisione nome `OrigineQuota` enum.** Il codice esistente ha già un enum
  `OrigineQuota` usato in `regole_calcolo` come indicatore di provenienza/audit
  (`CALCOLO_AUTOMATICO`, ecc.) — semantica diversa da `OrigineQuota` di questo spec
  (tipo economico dell'addebito). Prima dell'implementazione: rinominare uno dei due.
  Proposta: rinominare l'esistente in `SorgenteCalcolo` (o `MetodoGenerazione`) e
  riservare `OrigineQuota` alla semantica economica dello spec. Impatto: solo il JSON
  `regole_calcolo` e chi lo legge — verificare i consumer prima del rename.
- **D10 — Preservazione `meta_storico` / `dettagli_saldo`.** Il JSON `regole_calcolo`
  porta `dettagli_saldo` con la provenienza storica del saldo (esercizio di origine,
  conguaglio deliberato, ecc.). Quando si crea la cella `rate_quota_origine` per
  `saldo_iniziale`, valutare: (a) colonna JSON nullable `meta_json` sulla cella — accesso
  diretto senza join; (b) riferimento implicito via `rate_quota_id` → `regole_calcolo`
  originale — zero ridondanza ma lettura in due passi. In entrambi i casi il dato va
  preservato: è l'unica fonte di verità sulla provenienza del saldo per i subentri v1.11.

## 12. Piano di test (Pest)

Su SQLite in-memory. Suite completa e non filtrata prima di dichiarare l'RC — un
`Event::fake()` nei test del controller **non** prova la correttezza dell'emissione: i
listener reali non girano.

1. **33,33% × 3 chiude in cent**: `T=10000`, `[3333,3333,3333]` → `[3333,3333,3334]`, `Σ=10000`.
2. **Multi-immobile penny-perfect** (l'esempio §5.4): verifica INV-1, INV-2, INV-3, INV-4.
3. **Compensatrice = ultima rata non nulla**: `saldo=[100,0,0]` → tutto su r1, r2/r3 = 0.
4. **Rata a 0% legittima**: cella con `importo_cents = 0` ammessa, non null.
5. **`prima_non_nulla` speculare e robusto**: stesso input di §5.4 con `metodo=prima_non_nulla`;
   compensatrice=r1, r2/r3 calcolate con `intdiv`; verifica INV-1 rispettato; Σ rata esatta.
   Caso edge: un'origine con una sola rata → rata unica è sia prima che ultima non nulla →
   riceve tutto T indipendentemente dalla percentuale inserita.
6. **Idempotenza della rigenerazione**: rigenerare prima dell'emissione produce celle identiche.
7. **No doppia emissione (INV-7)**: l'allocazione di `saldo_iniziale` non crea scritture
   di emissione; il credito di apertura resta invariato.
8. **Emissione mista**: rata con `preventivo` + `saldo_iniziale`; la scrittura di
   emissione riflette **solo** la quota di preventivo.
9. **Imputazione incasso per origine** (se si adotta D3): un incasso parziale riduce il
   credito e la proiezione "incassato per origine" quadra.
10. **Blocco post-emissione**: tentare di modificare percentuali/celle su rate emesse →
    eccezione; la correzione passa da storno.
11. **Backfill**: dato un piano legacy, dopo la migrazione `rate_quote.importo == Σ celle`
    su tutto il dataset.
12. **Tolleranza validazione**: `[3333,3333,3333]` passa (sub-soglia); `[5000,5000,5000]`
    (150%) blocca.
13. **Migrazione da `regole_calcolo`**: dato un set di `rate_quote` con JSON contenente
    `quota_pura_gestione` + `saldo_usato`, dopo lo Step 1 del backfill: (a) ogni
    `rate_quota` ha esattamente le celle attese per origine; (b) INV-3 è soddisfatto su
    tutto il dataset; (c) le Rata Zero (`numero_rata=0`) generano solo cella
    `saldo_iniziale`, mai `preventivo`; (d) le quote pre-v1.9 senza `regole_calcolo`
    cadono nel fallback `preventivo` con `importo_cents = importo`.
